# 剩余实验路线图（按执行顺序）

**日期:** 2026-06-01 · **基准:** 第 5 章实验(40 runs)全部完成,论文 §5 实验覆盖率从 0%→85%

## 优先级体系

| 优先级 | 定义 | 触发条件 |
|--------|------|---------|
| **P0** | 闭合当前已有 infra 的缺口,每项 ≤2h,立即可做 | 现有 harness + 已有 instrumentation |

## P0:立即可做(已有 infra,≤2h 每项)

### 实验 1 — §5.4 闭合:断开网格(Partition Grid)

**为什么排第一:** 这是第 5 章实验**唯一的未闭合缺口**。40 runs 证明了 recFetch=0 在 0–10% loss 下恒成立,精炼了 H3 的边界——但没有在断开的**对侧**测量。补上断开网格后,§5.4 就有了完整的定量:安全地带多宽(0–10% loss)+ 断崖在哪里(断开多久触发 PULL)以及在触发后如何缩放(Δ_recover 的剂量响应)。

| 项目 | 值 |
|------|-----|
| **论文落点** | §5.4(完整定量);§5.6(台账升级);§9(诚实边界) |
| **设计** | n=7,扫 disconnect_duration(30/60/90s)×Δ_recover(0/500/1000ms),2 reps |
| **运行数** | 3×3×2 = **18 runs** |
| **预计时间** | ~1.5h |
| **复用** | 关键路径轮转 harness(`phaseA_criticalpath_partition.ps1`)已含 disconnect→reconnect 逻辑;只需把固定 90s 断开改为参数扫描 |
| **产出** | recFetch 计数 + t_resume 作为(partition_duration, Δ_recover)的函数;OLS 得出断开时长→recFetch 的斜率;证实"断崖"的存在与形状 |
| **风险** | 极低——Phase A 已验证单点 `docker network disconnect 80s` → 46 hits;现在只是扫参数 |

### 实验 2 — §7.3 ρ 轴独立扫描(Fault Frequency)

**为什么排第二:** §7.3 声称"当恢复频率 ρ 越过临界值 ρ\*,优势翻转"——但**从未在部署中扫过 ρ**。现有 harness 一次故障一次恢复,相当于 ρ = 1/run;真正的 ρ 扫描需要每 200s 测量窗内注入多次故障(如 0/1/2/4/8 次)。这是 §7.2 成本模型唯一完全未测的自变量。

| 项目 | 值 |
|------|-----|
| **论文落点** | §7.3(从定性→部署标定);§7.2(ρ\* band 的第二组独立验证) |
| **设计** | n=7,cert OFF,固定 Δ_recover=1000ms(迫使信号放大),扫 fault_count(0/1/2/4/8 per 200s 窗),3 reps |
| **运行数** | 5×3 = **15 runs** |
| **预计时间** | ~1.5h |
| **复用** | 关键路径 rotation harness;只需把"1 次 rotation"改为"每窗 N 次 rotation" |
| **产出** | t_resume 和 recFetch 作为 ρ(fault/commit)的函数;OLS 回归 cadence vs ρ;独立验证 §7.6.3 的 ρ\* band(当前仅从 Δ_save/excess 推导,非直接测量) |
| **风险** | 中——多轮 rotation 的时序需要仔细编排(N 次故障均匀分布在 200s 窗内,而非连续);可能需要 1-2 轮脚本调试 |

## P1:需要新 harness(每项 ~2-4h)

### 实验 3 — §4.5 负载大小扫描(Payload Size × Three Paths)

**为什么排第三:** §4.5 声称三个不变量"异质"——可用性是"物理型"的(代价随数据大小缩放),非等价性和因果历史是"逻辑型"的(代价与数据大小无关)。这个声称**从未被实验检验**。现在三条路径都有 instrumentation,只需加一个可变的 tx payload。由于 P0 实验 1-2 会提供 §5 和 §7 的紧要数据,这项可以排在它们之后。

| 项目 | 值 |
|------|-----|
| **论文落点** | §4.5(从分析性分类→定量标定) |
| **设计** | n=7,固定无故障,扫 tx_payload_size(1KB/10KB/100KB/1MB),测量三条路径的 per-call latency + per-commit count |
| **运行数** | 4×3 = **12 runs** |
| **预计时间** | ~3h(主要耗时:重新编译带不同 payload 生成的 Sui binary;或改用脚本向已有网络注入可变大小的交易) |
| **复用** | 第 5 章 instrumentation(三条路径已有) + compose |
| **产出** | 可用性路径(Path C network fetch)的 per-byte 成本斜率;eq/causal 路径的平坦验证;per-byte latency 作为定量补充 §4.5 |
| **风险** | 中偏高——payload 生成在 Sui 中不直接可控(需要构造不同大小的 Move 交易或修改 test 交易生成器);替代方案:用 `sui client pay` 发送不同大小的转账,测量验证者侧的路径延迟 |

### 实验 4 — §7.5 网络非对称(Per-Validator Bandwidth)

**为什么排第四:** §7.5 声称"认证的事前均摊在不利网络下是鲁棒性资产",并用 DispersedLedger 作旁证——但没有自身的网络非对称实验。在低带宽验证者下测量 cert ON vs OFF 会直接支撑这个 claim。放在 P1 是因为需要把 `tc rate` 而非 `tc loss` 接入 compose,且需要 cert ON arm(已有)。

| 项目 | 值 |
|------|-----|
| **论文落点** | §7.5(从定性引用→部署对照) |
| **设计** | n=7,固定 fault-free,低带宽 1-2 个验证者(1Mbps),cert ON vs OFF,3 reps |
| **运行数** | 2(cert)×3 = **6 runs**(+ 对称基线 = 9 runs) |
| **预计时间** | ~2h |
| **复用** | cert-gate(Route A1),compose,已有 metrics |
| **产出** | cadence 差异(对称 vs 非对称)在 cert ON 和 OFF 下的衰减幅度;验证"认证在非对称下更鲁棒"的 claim |
| **风险** | 低——`tc rate` 比 `tc loss` 更简单,不太可能出编排 bug;限制带宽本身就是一种可控实验 |

### 实验 5 — §7.4 GST 抖动(部分同步退化)

**为什么排最后(P1 末尾):** §7.4 的 ρ–Δ_recover 耦合是论文最弱的定量 claim(目前完全定性)。但 GST 抖动的实验设计**本身有概念难度**——什么是"注入 GST 抖动"的可操作定义?候选方案:周期性断开+重连(模拟 GST 前→GST 后的反复切换),测量 cadence 和 recFetch 的瞬态行为。先排后,因为实验 4 的非对称实验可能为"部分同步退化"提供一个更干净的替代操作化。

| 项目 | 值 |
|------|-----|
| **论文落点** | §7.4(从纯定性→机制演示) |
| **设计** | n=7,固定 Δ_recover=500ms,扫 GST_jitter_period(每 30/60/90s 断开 5s),3 reps |
| **运行数** | 3×3 = **9 runs** |
| **预计时间** | ~2h |
| **复用** | 关键路径 rotation harness(断开→重连逻辑) |
| **产出** | 反复 GST 抖动下 cadence 的衰减曲线;recFetch 累积趋势;验证"拥塞反馈"的定性 |
| **风险** | 中——GST 抖动的操作化不够标准;结果可能难解释(断开后 cadence 恢复的瞬态混叠);论文 §7.4 可能不需要独立的部署实验来支撑其定性讨论 |

## P2:深工程(单独评估,不纳入常规路线图)

### Deep-1 — 跨引擎真 RBC Benchmark(非可用性证书)

| 项目 | 值 |
|------|-----|
| **内容** | 在 Mysticeti 中重建 Narwhal 风格的 RBC 确认轮(独立投票/ack 通道 + 2f+1 签名聚合),与 Route A1 的可用性证书对照,获得"真实 RBC 签名开销"vs"可用性证书等待开销"的定量差异 |
| **工程量** | **深 consensus 子项目**。PHASE0_SPIKE §2 已分析:需要新的消息类型(投票/ack)、新的网络路径、签名聚合逻辑。Narwhal 实现已从 codebase 移除(仅剩 `ConsensusChoice::Narwhal` enum 残桩) |
| **预计时间** | 2-4 周(设计+实现+测试+部署) |
| **决策点** | 仅当论文需要从"成本结构标定"升级为"绝对延迟对照"时才值得做;当前 Route A1 的可用性证书已经足以支撑 §7.6.3 的核心 claim(Δ_save 为正、cert 恢复更便宜、存在 ρ\* 翻转) |

### Deep-2 — n=10 与 n=4 certified 臂

| 项目 | 值 |
|------|-----|
| **内容** | 构建 n=10 compose(当前只有 n=7 和 n=4);跑关键路径 rotation 跨规模复现(n=10 单点验证) + n=4 certified arm(已有 n=7 cert arm,需 n=4 compose 兼容 cert-gate env) |
| **工程量** | 中。n=10 compose 需要新的 genesis + validator config(仿 n=4 的 `prepare_multivalidator_n4.ps1` 模板);n=4 cert arm 已有 infra(代码已支持) |
| **预计时间** | n=10 compose ~2h;n=4 cert arm ~1h 测试;合计 ~3h + ~3h 运行 |
| **决策点** | n=10 是一个"锦上添花"的规模点(已有 n=4/n=7 足以论证委员会结构依赖);n=4 cert arm 如果做,可以验证 §7.6.3 的 ρ\* 估算是否跨规模成立——但论文目前已明确标注这些限定 |

## 推荐执行顺序(一次性跑通)

```
第 1 天（~3h）:
  ├─ P0-1: 断开网格 (18 runs, ~1.5h)
  └─ P0-2: ρ 轴扫描 (15 runs, ~1.5h)
     └─ 如果时间够,两实验可并行(n=7 compose 复用,串行更安全)

第 2 天（~5h）:
  ├─ P1-1: 负载大小扫描 (12 runs, ~3h,需 payload 生成)
  └─ P1-2: 网络非对称 (9 runs, ~2h)

第 3 天（~2h,可选）:
  └─ P1-3: GST 抖动 (9 runs, ~2h)
     └─ 仅当实验 1-4 全部完成后仍有时间,且 §7.4 需要独立实验

P2 决策点:
  └─ 用户决定是否投入 Deep-1(真 RBC)或 Deep-2(n=10/n4 cert)
```
