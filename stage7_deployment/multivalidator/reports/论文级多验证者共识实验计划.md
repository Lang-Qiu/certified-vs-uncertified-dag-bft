# 论文级多验证者共识实验计划

## 目标

本阶段以真实 `N=7, f=2` 多验证者部署作为主证据来源，验证区块链流水线在正常、网络延迟、丢包、单验证者暂停和双验证者压力条件下的共识可用性、检查点推进、交易提交和恢复表现。

核心原则：

- 使用 `sui genesis --committee-size 7` 生成官方 genesis、validator yaml、fullnode yaml 和密钥材料。
- 每个验证者运行在独立 Docker 容器中，通过 `sui-node --config-path <validator-yaml>` 启动。
- 内部 swarm 或 test-cluster 只可作为预校准或排障，不作为论文主证据。
- 所有实验串行执行，一次只运行一个场景，降低 16GB 主机内存下的测量干扰。

## 实验矩阵

矩阵文件：`stage7_deployment/multivalidator/config/experiment_matrix.yaml`

| 场景 | 重复次数 | 故障注入 |
| --- | ---: | --- |
| `baseline` | 10 | 无 |
| `delay_low` | 10 | `validator-1` 延迟 50ms，抖动 10ms |
| `delay_high` | 10 | `validator-1` 延迟 200ms，抖动 40ms |
| `loss_low` | 10 | `validator-1` 丢包 1% |
| `crash_one_validator` | 10 | `validator-1` 暂停 30s 后恢复 |
| `two_validator_pressure` | 10 | `validator-1` 延迟 150ms/30ms，`validator-2` 丢包 2% |

完整矩阵共 60 次运行。每次运行保留独立 `run_id`、配置、日志、探测、工作负载、故障时间线、指标和 manifest。

## 串行运行流程

正式运行前先生成环境快照：

```powershell
powershell -ExecutionPolicy Bypass -File .\stage7_deployment\multivalidator\scripts\check_docker_budget.ps1
python .\stage7_deployment\multivalidator\tools\validate_manifest.py --environment .\stage7_deployment\multivalidator\data\manifests\environment_snapshot.json
```

只生成矩阵计划，不启动容器：

```powershell
powershell -ExecutionPolicy Bypass -File .\stage7_deployment\multivalidator\scripts\run_experiment_matrix.ps1 -MaxRuns 0
```

先运行 1 次正式链路试跑：

```powershell
powershell -ExecutionPolicy Bypass -File .\stage7_deployment\multivalidator\scripts\run_experiment_matrix.ps1 -MaxRuns 1 -StartCompose -WorkloadDurationSeconds 60
```

确认单次运行的 metrics 和 manifest 后，再运行完整矩阵：

```powershell
powershell -ExecutionPolicy Bypass -File .\stage7_deployment\multivalidator\scripts\run_experiment_matrix.ps1 -MaxRuns 60 -StartCompose -WorkloadDurationSeconds 60 -ContinueOnFailure
```

控制器会按顺序执行：

1. 生成本次运行的官方 `N=7` genesis 配置。
2. 启动 7 个 validator 容器和 1 个 fullnode 容器。
3. 等待 fullnode RPC 检查点推进到至少 1。
4. 执行 warmup RPC probe。
5. 注入场景定义的网络或暂停故障。
6. 执行 fault-window RPC probe。
7. 通过 Docker 化 `sui client transfer-sui` 提交真实交易。
8. 对暂停类故障执行恢复，并记录恢复时间。
9. 执行 recovery RPC probe。
10. 采集容器状态、日志、指标、manifest，并关闭容器。

## 证据结构

每次运行保存在：

```text
stage7_deployment/multivalidator/data/runs/<run_id>/
```

关键文件：

- `official-genesis/`：官方 Sui genesis 输出和 validator/fullnode 配置。
- `network_plan.json`：实验拓扑、场景、重复编号和容错参数。
- `controller_record.json`：串行控制器状态、开始结束时间、故障和错误记录。
- `evidence/rpc_probe/*.jsonl`：warmup、fault window、recovery 阶段 RPC 探测。
- `evidence/workload/actual_transfers.jsonl`：真实 `transfer-sui` 交易提交记录。
- `evidence/fault_timeline.jsonl`：故障注入和恢复时间线。
- `evidence/container_state/`：`docker ps`、`docker inspect` 和容器日志。
- `metrics/consensus_metrics.json`：论文可引用的结构化指标。
- `manifest.json`：所有证据文件的 sha256、字节数和来源登记。

## 质量门槛

正式矩阵完成后，至少需要满足：

- 每个 run 的 `manifest.json` 校验通过。
- 每个非失败 run 的 `validator_count=7`、`fault_tolerance=2`。
- baseline 场景 RPC 可用率接近 1.0，且真实交易成功率可解释。
- 故障场景必须保留 `fault_timeline.jsonl`，暂停类故障必须记录 `recovery_complete`。
- 所有异常运行不得删除，应保留为失败证据，并在论文中作为实验限制或排障记录处理。
